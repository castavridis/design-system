# figma-token-sync

Keep this repo's design tokens and its Figma design system in sync, **both
directions**. This skill is the **project-specific glue** — where the tokens
live, how they're built, and the exact code↔Figma mapping. It does **not**
re-implement the Figma Plugin API: it delegates the mechanical work to the
Figma plugin skills and tells them the repo's rules.

## Source of truth & guardrails

- **The only writable token source is `src/pmndrs-design-book.ts`.** Every
  artifact in `dist/` is generated by `pnpm build` — **never hand-edit `dist/`**,
  and never edit tokens anywhere else.
- Figma reads from the **built artifacts**, not from `src`. Always `pnpm build`
  first so `dist/` is current.
- Colours are **authored in OKLCH** in `src` (the trailing hex is a comment).
  Figma stores sRGB. See [the OKLCH round-trip rule](#the-oklch-round-trip-rule)
  — a pull must never clobber OKLCH source with raw hex.
- The token set defines **no light/dark theming** — `brand.dark`/`brand.light`
  are two neutral brand colours, not modes. Mirror the code 1:1 with
  **single-mode** collections. Do **not** invent Light/Dark modes; note it as a
  future extension if the user asks for theming.
- Typefaces are named **once**, in `families` in the design book. `family.*` (the
  bare name, the only shape Figma can bind), `fonts.*` (the CSS stack), the Google
  Fonts request in `scripts/build.ts` and the faces `scripts/figma-page.ts` loads
  all derive from it. Add a typeface there, never in one of the four consumers.

## Delegate the mechanics

Load these alongside this skill — this skill says *what/where*, they say *how*:

- **Writing to Figma** → `figma-generate-library` + `figma-use` (mandatory before
  any `use_figma` call). They own collections, variables, scopes, aliases,
  components, and the phase/validation discipline.
- **Mapping components/tokens to code** → `figma-code-connect`.
- **Reading from Figma** → `get_variable_defs` and read-only `use_figma`.

The authoritative, repo-specific mapping (types, scopes, naming, aliases, the
hex→rgb helper) is in **[references/token-mapping.md](references/token-mapping.md)** —
read it before Phase 1 of either workflow.

## Workflow A — Push (code → Figma)

1. **Build & emit.** `pnpm figma:emit`, which runs `pnpm build` first. The script
   is `scripts/emit-figma-tokens.mjs` **in the repo**. This skill used to ship its
   own copy that resolved the repo root from its own file location — which lands
   on the main checkout even when invoked from a worktree, so it silently emitted
   the wrong tree's tokens. Do not reintroduce a second copy.
   This writes `dist/figma-tokens.json`: one verified entry per token
   (`key, collection, figmaName, type, scopes, codeSyntax, value | aliasOf`).
   **The push scripts consume this file — never transcribe hex or values by eye.**
2. **Phase 0 — Discovery.** Inspect the target Figma file (existing collections,
   variables, conventions). If there's no file yet, create one (load
   `figma-create-new-file`). Print a gap analysis: code-only, Figma-only, conflicts.
3. **Phase 1 — Foundations.** Create the `family`, `brand` and `fonts` collections
   (single mode `Value`) and their variables from `dist/figma-tokens.json`, per
   [token-mapping.md](references/token-mapping.md):
   - `type`, `scopes`, and WEB `codeSyntax` (`var(--…)`) exactly as emitted.
   - **`brand/radius` MUST be a `VARIABLE_ALIAS` to `brand/space`** (the entry has
     `aliasOf`, no `value`) — never a duplicated `16`. This preserves the
     live-reference behaviour across the bridge.
   - Colours: use the emitted 0–1 `{r,g,b}` directly (already sRGB, Figma-ready).
4. **Phase 2 — Foundations docs.** A Foundations page: palette swatches, a type
   specimen (`brand.headline` + `fonts.*`), spacing/radius bars, and **gradient
   specimens** (see [gradients](#gradients-are-not-variables)).
5. **Phase 3 — Components.** The components are declared in
   `src/components/contract.ts` — props, the variant property, and the theme slot
   each variant binds. Build the Figma component set from that declaration, never
   from the markup: the contract is what `demo/elements.js`, the Figma set and
   Code Connect all read. `pnpm figma:audit` reports where a set has drifted.
6. **Phase 4 — Code Connect.** Map the token module (`pmndrs-design-tokens`,
   `cssVar('brand.radius')` → `var(--brand-radius)`) and the component sets via
   `figma-code-connect`.

## Workflow C — The page (`demo/index.html` → Figma)

Same shape as the token push: decide what should exist, emit a self-contained
program, run it, record the ids.

1. **Emit.** `pnpm figma:page --snapshot` writes `dist/figma-page.json` (the page
   spec), `dist/figma-page.js` (the build program) and
   `dist/figma-page-snapshot.js` (the read-back program). It refuses to emit if
   the page uses a component with no recorded Figma id.
2. **Run** `dist/figma-page.js` through `use_figma`, then
   `pnpm figma:page --record <result.json>`. The program *returns*
   `problems`, `missingFonts` and `missingVariables` rather than throwing — read
   them.
3. **Audit.** Run `dist/figma-page-snapshot.js`, save the JSON, and
   `pnpm figma:audit <snapshot.json>` — it compares components *and* page
   composition. `--only=Nav,Search,Toc` scopes the component half when the
   snapshot covers only the components you just landed.

**Landing a new component** is four steps, in this order: declare it in
`src/components/contract.ts` (the build fails if a bound slot is missing from
either mode), build it in Figma bound to `theme/*`, record its id under
`components` in `figma/sync.json`, then mark its block in `demo/index.html` with
`data-component`. `pnpm figma:page` refuses to emit until the id is recorded,
which is the check that keeps the order honest — the page cannot instantiate a
component that does not exist.

**The rule that matters:** a block the contract declares is placed as
`createInstance()` of the component set already in the file — never redrawn.
Everything else becomes a labelled stand-in. Do not "improve" a stand-in into a
real design: that would be a Figma-only design with no owner in code, and the
audit would have nothing to compare it against.

Props are derived from the markup, so **never restate a variant in an
attribute**. `data-component` names the component; the class, the caption and the
`is-hl` lines say which variant it is.

The frame is **rebuilt in place** on every push — its children are replaced, the
node itself is not. Deleting and re-appending would detach every instance of it,
and the frame may well be a component (ours is). Its position and theme mode are
carried over for the same reason: where it sits and which mode it is viewed in
are Figma's decisions, not the code's. Its children are — audit first if
someone may have edited it in Figma. Its position is kept, and so is its
location: the push resolves the frame by the node id in `figma/sync.json`, so a
frame dragged to another page is followed rather than duplicated. If that id is
gone (a cut and paste mints a new one) it falls back to the recorded page, then
to `pageId` — the page the components live on — then to the frame's name. It
never creates a page. When someone moves the frame, re-record rather than
editing `sync.json` by hand: capture the current ids and run
`pnpm figma:page --record <result.json>`.

## Workflow B — Pull (Figma → code)

1. **Read Figma.** `get_variable_defs` (or read-only `use_figma`) for all
   `family/*`, `brand/*` and `fonts/*` variables and their resolved values.
2. **Diff.** `pnpm build`, then compare against `dist/tokens.json` (resolved
   values) and `dist/figma-tokens.json` (structure). Produce a **reconciliation
   report**: Figma-only, code-only, and value conflicts, each with provenance
   (Figma node vs `src` line).
3. **Decide forks.** For every conflict, surface both sides and ask which wins —
   reuse the fork protocol from `figma-generate-library` §6. Never silently pick.
4. **Apply.** Edit **`src/pmndrs-design-book.ts`** only (never `dist/`), following
   [the OKLCH round-trip rule](#the-oklch-round-trip-rule). Then `pnpm build` to
   regenerate every artifact.

## The OKLCH round-trip rule

Colours round-trip **by hex**, and Figma is sRGB while the source is OKLCH:

- On **pull**, compare Figma's value to each token's **resolved hex** (from
  `dist/figma-tokens.json` → `value.hex`). Flag a colour as changed **only when
  the hex actually differs** — identical colours in different notations are not a
  change.
- When a colour did change, hand the user the **new hex** and re-author it in
  `src` as `color('oklch(...)')` with the hex kept as the trailing comment
  (convert hex→OKLCH, or ask). **Do not replace an `oklch(...)` value with a raw
  hex string** — that would silently drop the authoring notation the repo depends
  on for deriving tints and rotating hues.
- Non-colour tokens (dimensions, font families) round-trip literally — no special
  handling.

## Gradients are not variables

The 3-stop system (16/50/84%), the adjacency rule, and the `brand.dark` /
`brand.light` exclusions live in code (`tokens.js`: `gradient`, `gradientColors`,
`assertGradientStops`) and stay **code-authored** — Figma variables can't express
them. In Figma, represent gradients only as **documentation specimens** on the
Foundations page, generated from `gradientColors` (every brand colour except the
two neutrals). Never try to round-trip a gradient into a variable.

## Verify

- After a push: `get_variable_defs` shows `family/*` + `brand/*` + `fonts/*` with
  the right scopes, `var(--…)` code syntax, `brand/radius` aliased to
  `brand/space`, and `brand/headline` aliased to `family/serif`. `fonts/*` must
  come back with an **empty** scope list — a stack Figma offers for binding is a
  binding that cannot resolve.
- After a pull: the report flags exactly the changed tokens, the `src` edit keeps
  OKLCH notation, and `pnpm build` regenerates cleanly.
- After a page push: `problems` is empty, and `pnpm figma:audit` on a fresh
  snapshot reports no drift. Check the instance count against the summary
  `pnpm figma:page` printed.
